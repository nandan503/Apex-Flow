01 · Problem & motivation

Logistics operations are usually spread across a spreadsheet,
a phone call, and someone's memory

The repository's module set defines the pain it targets: a shipment needs a vehicle, a driver, a route, a proof of delivery, an invoice, and a status trail — and those five artefacts normally live in five different places.

PROBLEM 1

⌛No shared status

“Where is my consignment?” is answered by calling the driver. The repo models this as an append-only shipment_status_history table instead.

PROBLEM 2

✍️No proof of delivery

Deliveries get disputed. The system gates the Delivered state behind a one-time code bound to the shipment, plus the receiver's name.

PROBLEM 3

🗂️Fleet compliance drifts

Insurance, permit, fitness and service dates are per-vehicle columns (insurance_expiry, fitness_expiry) so they can be queried at all.

PROBLEM 4

🔓“Student project” security

The interesting problem for this project: CRUD demos usually ship with open endpoints, SELECT *, weak OTPs and hardcoded secrets. The audit report attacks exactly that.

Why it is worth solving

The domain forces real engineering: multi-role authorisation, state machines, financial fields that must not be client-controlled, and time-based telemetry.

Why I built it (as evidenced)

The repo is dominated by quality machinery: 15-finding security audit, custom SAST rules, a full CI pipeline, IaC and an ops agent — 3,791 lines of docs (2,120), scripts (1,121) and workflow YAML (550) against 1,914 lines of API code (the client adds a further 4,327). Whatever the intent, the result is a repo where the evidence about the code is half the size of the code itself.

Who uses it

Four roles declared in the schema CHECK: ADMIN, MANAGER, DRIVER, CUSTOMER — with different visibility per endpoint.

02 · Project overview

One request path, five writes per booking

APEX FLOW is a single-origin web application: Flask serves the static client and the JSON API under /api, so there is no cross-origin hop in production.

Blueprint routes → @login_required/@require_role → service layer, which fans one booking out into 5 INSERTs and one commit(): shipment, status history, delivery+OTP, invoice, notification.

📤 OUTPUT
Dashboard KPIs, live map telemetry, OTP confirmation, invoices/CSV-JSON export.

Single JSON envelope

Every endpoint returns {success, message, data} from one helper — so the client has one error path.

Server owns the money

Status, payment status and cost are set in the service layer, never read from the body.

Delivery is an event

Honest scope limit

GPS “live tracking” is an interpolation simulation, and no external map, SMS or payment provider is integrated.

04 · Technology stack

Eight runtime dependencies, and a reason visible in the code for each

Frontend

HTML5CSS3 · custom propsVanilla JS<canvas> 2D

Why: no bundler, no framework — the same Flask process serves static_folder='frontend', so the whole app is one deployable unit. Charts and the map are hand-drawn on canvas rather than pulling in a charting or tile library. Responsive behaviour is media queries + a drawer, not a component library.

Backend

Flask ≥2.3,<4BlueprintWerkzeugflask-corsflask-limiter + limitspython-dotenv

Why: 26 JSON routes need routing, sessions and decorators — nothing more. flask-limiter buys the rate-limit requirement without hand-rolling a token bucket; limits is its storage backend. Werkzeug provides generate_password_hash / check_password_hash, so no extra crypto dependency is needed. dotenv is imported in a try/except ImportError so the app still boots without it.

Data

sqlite3 (stdlib)PostgreSQL via psycopg2-binaryRaw SQL + CHECK constraints

Why: zero-config persistence in dev, real RDBMS in prod, behind one get_db_connection() switch. No ORM: the queries are short, aggregate-heavy KPI SQL and an ORM would add a layer without removing hand-written SQL. Integrity is enforced in the schema (10-value status enum, FK cascade), so the API cannot corrupt state even if a route forgets to validate.

Security primitives

secrets.randbelowuuid4 (IDs)pbkdf2 hashessession cookie flags

Why: secrets is the CSPRNG — replacing random.randint for OTPs was finding F-04 in the audit. uuid4().hex[:8] IDs remove enumeration (F-13). Both are stdlib, so no dependency is added to fix a vulnerability.

Why: cheap static gates (syntax, secrets, SAST) run in <60 s on every PR; pytest is wired but has no test files to run yet (slide 13); pip-audit is informational by design (|| true) until a clean baseline exists.

Deployment & scripting

06 · How the system works

Anatomy of one write: POST /api/shipments

Chosen because it crosses every layer — session, authorisation, validation, four tables, an OTP, an invoice and a log line.

1Client → fetchAPI('/shipments', {method:'POST'})
Form is read field-by-field in shipments.js; the envelope contract is assumed, not validated.
2Edge → cookies + limiter
Default limit checked (200/min/IP) · X-RateLimit-* attached · CORS allowlist evaluated.
3Authorise → @login_required
Presence of session['user_id'] only — no CSRF token, mitigated by SameSite=Lax.
4Validate → hand-written checks
Route requires pickup and destination; everything else is defaulted or coerced with float()/int().
5Compute → service layer
Allowlist filter · SHP-xxxxxxxx id · server-set status='Booked', payment_status='Pending' · cost formula · 6-digit CSPRNG OTP with +30 min expiry.
6Persist → 5 INSERTs, one commit
shipments → shipment_status_history → deliveries(OTP) → payments(18 % GST) → notifications. single transaction, no rollback wrapper
7Respond → 201 + audit log
{success:true, message, data:<shipment>, shipment_id} — read back through a second SELECT; the OTP is never in it.

Measured on a live instance

Locally, one complete booking (auth + 4 inserts + commit + read-back) finished in 10 ms. That is not a benchmark — it shows where the time isn't going: no pool, no cache, no network hop, no queue.

Two shortcuts visible in this path

① The status flow PUT /shipments/:id/status skips validation entirely — any of the 10 enum values can be set from any state.
② If an INSERT raises, the connection is closed only on the success path (slide 14 shows what that costs).

Why this matters

Authorisation is a property of the route definition, not of the handler's discipline: forgetting it is visible in a diff, and a custom Semgrep rule (apexflow-unauthenticated-route) fails CI when a route in routes.py has neither decorator. 401 and 403 are distinct, and each is logged with the caller identity — the audit trail and the enforcement are produced by the same function, so they cannot drift apart.

After lockout, the correct code is also refused — the counter, not the code, decides. And GET /api/deliveries returns 12 columns with no otp_* among them.

⚖Trade-offs I accept in this design

  • Plaintext at rest. Hashing is cheap here (compare sha256(input)), so plaintext is a choice, not a constraint: it lets an operator read the code back to a driver — which is also why the UI still tries to render it. A hash column plus a reveal-once endpoint would keep the workflow without the table-wide exposure.
  • Comparison is not constant-time (!= on short digit strings); the 5-attempt lockout is what actually bounds the attack.
  • No re-issue endpoint. After the TTL there is no way to get a new code except by editing the DB.
  • Lockout is per shipment, not per account — cheap to bypass by switching shipments, but it cannot lock a receiver out of the platform.

09 · Algorithms & domain logic

Four algorithms — two real, two deliberately heuristic

⇄Shipment lifecycle — constraints, not transitions

Booked→Confirmed→Picked Up→At Warehouse→In Transit→Out for Delivery→Delivered
exception states: Delayed Cancelled Returned — the 10 values of the schema's CHECK(status IN …)

Legal values are declared in SQL, so both engines and both clients obey one definition. I verified an invalid value fails closed: PUT {"status":"Teleported"} → IntegrityError: CHECK constraint failed.

No edge validation: update_shipment_status() never reads the current value, so any state may follow any state. Live check: Delivered → Booked returned 200 — the column was moved backwards with no complaint.

Every accepted transition appends an immutable history row with location, updated_by (from session, F-08) and notes — that table, not the status column, is the audit record. The missing piece is ~15 lines: a dict of allowed successors, checked before the UPDATE.

₹Pricing — deterministic formula, non-deterministic result

backend/services.py · _calculate_shipping_cost()
base = 1500.0 ; per_kg = weight_kg * 2.5distance_factor = abs(hash(pickup + destination)) % 3000 + 500  # ⚠ saltedreturn round(base + per_kg + distance_factor * 0.5, 2)

What I measured: the same shipment (Ludhiana → Delhi, 8 000 kg), priced in seven independent processes, came out between ₹21 845 and ₹23 042. Python salted str hashing with PYTHONHASHSEED, so hash() is only stable inside one process.

And it is not a distance — it is a pseudo-random number derived from the letters of two city names, so a restart changes the price of an identical booking. Fix: the routes table already holds real distances; use them, or zlib.crc32 for a stable pseudo-distance.

🛰“Live” tracking — a clock, not a GPS feed

backend/tracking.py · get_live_tracking_data()
t = (int(time.time()) % 100) / 100.0          # 0 → 1, every 100 slat = start[0] + (end[0] - start[0]) * current_time_factordist_remaining = haversine_approx * (1.0 - current_time_factor)speed = 58 + int(math.sin(time.time()) * 12)                # 46–70 km/heta_minutes = int((dist_remaining / max(speed, 30)) * 60)
  • Verified: progress went 10 % → 14 % in 4 s while the front-end polled every 4 s, and all three active shipments shared one factor — trucks move in lockstep, and rewind when the 100 s window wraps.
  • Distance uses √(Δlat²+Δlng²)×111 — a flat-earth approximation, fine for a demo, wrong across India's latitude span.
  • With no in-transit shipment the module returns a hardcoded SHP001 record, so the UI always looks alive.
A real feed needs a device ingest endpoint + a position table; the current shape already supports that swap.

◇Why the safety design is the interesting part

  • Read-only by construction: _http_get only; endpoints that return secrets are never called; ipAllowList/sshAddress are dropped from the payload.
  • Explicit exit codes (0 live, 3 failed-with-bundle, 4 no matching service, 5 ambiguous, 6 timed out) so CI branches on meaning, not on grep.
  • Over-redaction is a deliberate preference — the module says commit SHAs and request IDs must survive, credentials must not.
  • Loop protection: per-SHA counter, MAX_ATTEMPT = 1, no push to main, no auto-merge, auto-deploy disabled on the fix branch.

!What it cannot actually do (verified)

  • Both fixers only diagnose: attempt_syntax_fix prints the file and line and returns 2; it never edits. The import fixer finds a missing package but refuses to guess a version.
  • Consequence: result == 0 is unreachable, so the PR-creation step never fires — the automation escalates reliably but does not self-heal. (Its own docstring still says “add it and validate”.)
  • docs/render-agent.md claims “9-layer sanitization”; the implementation is 3 layers with 10 patterns.
  • Counter files are gitignored, so the counter is per-run; cross-run protection rests on one env var.

The three gaps, and their one-line fixes

  1. Per-route limits never attach. limiter.limit(...) is applied to the view after register_blueprint(), which flask-limiter does not re-read. Fix: decorate the function in routes.py.
  2. Leaked DB connections on failure. On an exception between get_db_connection() and conn.close(), the connection stays open holding SQLite's write lock → subsequent writes fail with database is locked. Fix: try/finally or a @contextmanager.
  3. Client identity vs. owner field. customer_id bypasses the allowlist (slide 8); FK violation is the only thing that stops it.

14 · Challenges & engineering decisions

Challenge → Decision → what it cost

CHALLENGE

One codebase, two databases

SQLite for a zero-setup demo, PostgreSQL for a real deploy — with different row types, placeholders and DDL keywords.

DECISION

A 90-line adapter, not an ORM

PostgresCursorWrapper rewrites ?→%s and strips AUTOINCREMENT; PostgresRow(dict) adds __getitem__(int) so row[0] works; connection choice is one if on DATABASE_URL; a failure falls back to SQLite so a demo never dies.

COST

Naive rewriting + a dangerous fallback

Text replacement is not a parser: it rewrites inside string literals too. The fallback can silently persist to a file instead of the production DB, and stripping AUTOINCREMENT leaves no sequence for history_id. Migrations: an idempotent ALTER TABLE inside except Exception: pass.

CHALLENGE

Authorise 26 routes, 4 roles, and one object-ownership rule

Plus keep every denial visible in a log.

DECISION

Sessions + two decorators, no JWT

The browser is the only client, so a signed HttpOnly cookie beats a bearer token the page must store. Ownership is enforced twice on purpose — in the list query and again on the detail read.

COST

Same-origin lock-in + coverage by hand

No token means no native client without rework; CSRF rests on SameSite=Lax alone; and per-route protection is only complete if someone decorates every new route — 25 of 26 today, with a Semgrep rule as the only backstop.

CHALLENGE

“Real-time” tracking with no GPS, no map key, no socket server

DECISION

Deterministic simulation + 4 s polling + <canvas>

Position is interpolated between two city coordinates by a clock-derived factor; the client draws the route itself, so there is no tile provider, no API key quota and no WebSocket infrastructure to grade.

COST

A demo that cannot be mistaken for the real thing — yet

All shipments share one clock (lockstep, rewinding every 100 s), the “no active shipment” case returns a fabricated row, and the fallback coordinate pretends any unknown city is Delhi. Honest only while the label says “simulation”.

CHALLENGE

Money and status must never be client-set — with no framework to help

DECISION

Explicit allowlist + constants + read-back

safe = {k for k in ALLOWED}, then status='Booked' as a literal, and the response is re-read from the DB so the client sees what was stored, not what it asked for.

COST

A hand-maintained list is a bug generator

One field read from data instead of safe re-opened the hole I measured; two aliases (customer/pickup/weight) sit in the allowlist as UI conveniences; and the same payload shape is duplicated in 14 JS modules and 0 schema files. A Pydantic or JSON-Schema model would remove this entire class of mistake.

CHALLENGE

“Works on my machine” deployments, with no budget for a staging environment

DECISION

Give CI read-only access to the platform and bound its authority

Observe → classify → redact → (optionally) propose → escalate to a human; auth/* failures are never auto-fixed; the whole thing is stdlib urllib so CI needs no extra install step.

COST

Ceremony without a payoff yet

Because the fix stage never mutates a file, today's agent buys faster diagnosis but no shorter MTTR — and its documented guarantees (“9 layers”, “adds the missing package”) overstate the implementation.

15 · Limitations

What this is not — gaps, each with a reproduction

⚠Correctness & data

  • Booking is unusable for the CUSTOMER role: user_id is written into customer_id with no user→customer mapping — measured HTTP 500 on the FK.
  • A failed write leaks the connection and poisons every later write for the process’s lifetime.
  • Freight cost is a salted hash, so invoices are irreproducible; GST (18 %) is a literal.
  • Distance, ETA and speed come from string lengths and a clock; 3 seeded deliveries still carry 4-digit OTPs.
  • No state-machine validation; no indexes beyond PK/UNIQUE; no pagination, so LIKE ’%x%’ scans grow linearly.
  • DELETE /api/shipments/:id 500s whenever an invoice exists — the payments FK has no ON DELETE CASCADE (measured).

✗Security, quality & the client

  • 0 tests. Per-route rate limits inert. No CSRF token, no CSP / HSTS / X-Frame-Options, no password policy.
  • 24 client renderings put server strings into innerHTML with no escaping helper and no backend sanitisation. I confirmed the payload is stored and returned raw; I could not execute it — no browser here, and I will not claim a result I did not observe.
  • OTP plaintext and compared with !=; the Deliveries page renders the otp_code field F-05 removed, so operators see undefined. /deliveries and /notifications are not role-scoped.
  • Debug 500 pages echo SQL errors to the client; data/*.json is read by nothing; the login page hardcodes demo passwords in onclick. Docs claim an MIT LICENSE that is not in the tree, 6 Semgrep rules where 7 exist, and “9-layer” sanitisation where 3 layers exist.

◱Scale & ops limits

  • One-process assumptions everywhere: in-memory limiter (per worker), no Redis unless REDIS_URL is set.
  • One connection per service call, no pool, no shared transaction across the 5 writes.
  • Single Render web service; healthCheckPath: / only proves Flask serves HTML, not that the DB answers.
  • No container image, no lockfile — requirements.txt is range-pinned, so builds are not reproducible.

✦Deliberate scope decisions — not defects

  • Simulated telemetry and pricing formulas: the interesting engineering was the API contract and the security layer, not GPS plumbing — so they are labelled, not hidden.
  • No ORM. 1,914 lines of explicit SQL, every statement parameterised, integrity declared in the schema.
  • No JS framework or bundler. pip install -r requirements.txt && python3 backend/app.py is the whole setup a reviewer needs.
  • Read-only ops automation. It cannot merge, cannot push to main, cannot touch auth/*.

I list these because a limitation and a scope decision look identical in a feature list and behave very differently in a review.

The next six changes, in the order I would do them

⇢Ordered plan — each item deletes a bullet from the previous slide

  1. Correctness — ≈1 day. safe.get('customer_id') plus a real user→customer mapping; a @contextmanager around connections; a city-pair distance table replacing hash().
  2. Make the gates real — ≈2 days. Commit the harness I probed with as tests/test_api.py; attach limits at route definition; let test-sqlite fail when tests/ is absent.
  3. Close the obvious holes — ≈2 days. errorhandler(Exception) so clients stop seeing SQL text; an escapeHtml() helper or textContent in the client; role-scope /deliveries and /notifications; CSP + HSTS + ProxyFix.
  4. Make the domain honest — ≈1 week. A transition table for the 10 states; one serialiser (Pydantic or JSON-Schema) shared with the client; OTP hashed at rest with secrets.compare_digest, a re-issue endpoint and a real delivery channel.
  5. Then scale and ops — ≈1 week. Indexes + pagination; Redis for the limiter store; Alembic migrations; a lockfile and a container image; a /healthz that actually queries the DB.
  6. Finish the agent — ≈2 days. Let render_fix.py write the one fix it can safely write (a missing dependency line), so result == 0 becomes reachable and its PR path stops being dead code — or delete the stage and call it a diagnosis agent.

17 · Conclusion

A logistics app is easy. Proving what it actually does is the project.

Problem → Solution

Fragmented shipment status, no proof of delivery, drifting fleet compliance. APEX FLOW answers with one API that binds a booking to an audit trail, an OTP-gated delivery event and an invoice — 26 endpoints, 12 tables, 15 pages, 4 roles.

Key technical achievement

The security layer is not bolted on: 15 audited findings closed with decorators, allowlists, CSPRNG OTPs, hardened cookies, a PII-redacting structured logger, 7 SAST rules and a deployment agent that cannot leak a token — and I can name the file and function for each.

What the measurements bought

They turned a confident feature list into three real bugs — a broken customer booking, an inert rate limit, and a write path that locks itself after one failure — plus proof that the parts that matter (IDOR, mass assignment, OTP lockout, SQL parameterisation) genuinely work.

What I learned

Documentation is not enforcement: the audit says a control exists, the code says whether it fires. A single un-finally-ed connection is an outage. And a simulation must be labelled, or it becomes a claim.

Direction: correctness → tests that run in CI → closed authorisation gaps → real telemetry and routing. Not new pages: the system's surface area is already wider than its verification.
